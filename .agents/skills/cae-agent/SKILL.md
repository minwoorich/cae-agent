# CAE Agent

사용자의 자연어를 기본 인터페이스로 유지하고, PowerShell 명령은 내부 실행
수단으로 사용한다. 설치 상태와 현재 세션을 확인한 뒤 가장 작은 안전한 작업
단위로 Ansys를 제어한다.

## 기본 원칙

1. 저장소 루트에서 작업하고 Windows 환경인지 확인한다.
2. `.venv\Scripts\cae-agent.exe`가 있으면 이를 우선 사용한다.
3. 설치되지 않았다면 변경 내용을 설명하고 `setup.ps1` 실행 승인을 받는다.
4. 첫 CAE 작업 전에 `doctor`와 Workbench 상태를 확인한다.
5. 사용자의 공학적 요구사항에서 누락된 재료, 경계조건과 단위는 추측하지 말고
   결과에 영향을 주는 항목만 질문한다.
6. 실행할 시스템, 스크립트와 모델 변경 내용을 먼저 요약한다.
7. 스크립트, JSON 결과와 traceback을 작업공간에 보존하고 성공 여부를
   Ansys 반환값으로 확인한다.
8. 작업공간 용량이나 오래된 파일 정리를 요청받으면 먼저 `workspace status`와
   `workspace clean` dry-run을 실행하고, 삭제 후보를 보여준 뒤 승인을 받는다.
9. 사용자가 상태 화면이나 UI를 요청하면 `.[ui]` 설치 여부를 확인하고
   `cae-agent ui`를 localhost에서 실행한다. UI를 모델 편집기로 설명하지 않는다.

정확한 CLI 조합이 필요하면 [명령 참조](references/commands.md)를 읽는다.
SpaceClaim V261 스크립트를 새로 작성하거나 수정할 때만
[V261 스크립트 규칙](references/spaceclaim-v261.md)을 읽는다.

## 승인 경계

다음 작업은 사용자에게 대상과 영향을 설명하고 명시적으로 승인받은 뒤 실행한다.

- AI가 새로 생성하거나 수정한 스크립트를 Ansys 내부에서 처음 실행
- 기존 형상을 지우는 `--clear`
- 기존 프로젝트나 연결 데이터를 교체하는 `--overwrite`
- 사용자가 만든 기존 프로젝트, 형상, 재료, 경계조건 또는 해석 결과 변경
- 해석 실행처럼 라이선스와 계산 자원을 의미 있게 사용하는 작업
- `workspace clean --approve`를 사용하는 실제 파일 삭제

설치 상태 조회, `doctor`, `config show`, 세션 상태 조회와 파일 읽기는
변경 없는 진단이므로 별도 실행 승인을 요구하지 않는다. 새 작업공간이나 새
프로젝트에서 사용자가 명확히 요청한 생성 작업은 범위를 다시 확인한 뒤 진행한다.

## Codex 역할 선택

Codex가 이미 이 Skill을 사용해 최상위 조정자로 동작하는 경우에는 기본적으로
`generate`나 `run-agent`를 호출하지 않는다. 현재 Codex가 스크립트를 직접
작성·검토하고 `spaceclaim run` 또는 `mechanical run-script`로 실행하면
불필요한 두 번째 Codex 프로세스를 피할 수 있다.

다음 경우에만 내부 AI 명령을 사용한다.

- 사용자가 CAE Agent 자체의 `generate` 또는 `run-agent` 동작을 시험한다고
  명시한 경우
- 다른 자동화 환경에서 최상위 Codex가 스크립트를 직접 작성할 수 없는 경우

`run-agent`를 사용하더라도 `--approve-execution`은 사용자의 실제 승인 없이
추가하지 않는다.

## 표준 워크플로

### 1. 환경 준비

- `cae-agent --version`과 `doctor --json`을 실행한다.
- Python, Codex 또는 Ansys가 없으면 담당 기능과 설치 필요성을 구분해 설명한다.
- 기존 `cae-agent.toml`과 작업공간은 덮어쓰지 않는다.

### 2. 세션과 프로젝트 준비

- `workbench status`로 기존 세션을 먼저 확인한다.
- 세션이 없다면 `workbench start`가 장시간 유지되는 프로세스임을 알리고
  별도 숨김 프로세스로 시작한 뒤 상태를 재확인한다.
- 새 프로젝트가 필요하면 출력 경로와 기존 파일 존재 여부를 확인한다.
- `--overwrite` 없이 새 프로젝트를 생성한다.

### 3. 스크립트 작성과 검토

- SpaceClaim과 Mechanical 스크립트를 구분한다.
- 모든 새 주석과 docstring은 자세한 한국어로 작성한다.
- 단위, 바디 이름과 시스템 이름을 명시한다.
- 원본 파일을 덮어쓰지 말고 작업별 새 파일을 만든다.
- 실행 전에 사용자에게 스크립트 경로와 예상 모델 변경을 보여준다.

### 4. 실행과 검증

- 승인 후 대상별 실행 명령을 사용한다.
- SpaceClaim 결과 JSON, Mechanical 응답과 Workbench 저장 여부를 확인한다.
- 명령 종료 코드만으로 성공을 단정하지 않는다.
- 생성된 바디 이름, 개수 또는 요청한 해석 객체 등 확인 가능한 결과를 보고한다.

### 5. 실패 복구

- traceback과 보존된 스크립트를 읽어 원인을 분류한다.
- 사용자 경로, 토큰과 라이선스 정보를 외부 프롬프트나 Issue에서 가린다.
- 실패한 파일을 변경하지 않고 수정본을 새 파일로 만든다.
- 같은 작업을 무제한 반복하지 않는다. 설정된 `max_retries`를 상한으로 삼는다.
- 모델 삭제나 초기화가 필요한 수정은 다시 승인을 받는다.

### 6. 작업공간 정리

- `workspace status`로 폴더별 파일 수와 크기를 먼저 확인한다.
- `workspace clean --older-than DAYS`를 승인 없이 실행해 삭제 후보만 계산한다.
- `input`과 `results`는 자동 정리 대상이 아님을 사용자에게 알린다.
- 후보 수, 총크기, 보존 기간과 건너뛴 심볼릭 링크를 보여준다.
- 사용자가 실제 삭제를 명시적으로 승인한 뒤에만 `--approve`를 추가한다.
- 세션 메타데이터 때문에 차단되면 파일을 강제로 지우지 말고 Workbench와
  Mechanical을 정상 종료한 뒤 다시 상태를 확인한다.
- 실제 삭제 후 감사 로그 경로와 부분 실패 내역을 보고한다.

### 7. 로컬 대시보드

- UI는 환경, 세션 메타데이터, 작업공간과 정리 승인을 확인하는 보조 화면이다.
- NiceGUI가 없으면 `setup.ps1 -WithUI` 또는 `.[ui]` 선택 설치를 안내한다.
- `cae-agent ui`는 `127.0.0.1`에만 바인딩하며 외부 공개 방식을 만들지 않는다.
- 브라우저를 열지 않아야 하면 `--no-browser`를 사용한다.
- UI의 세션 표시는 메타데이터 기준이므로 실제 CAE 작업 전에 CLI ping을 확인한다.
- UI 업로드는 허용된 파일을 `workspace/input`에 새로 저장하는 용도로만
  사용하고, 기존 파일 덮어쓰기나 업로드 직후 자동 실행을 허용하지 않는다.
- 입력 파일 라이브러리의 체크박스는 향후 채팅에 전달할 파일을 준비하는
  선택일 뿐 실행 승인이 아니다. 채팅 연결 전에는 선택 파일이 Codex에
  자동으로 전달됐다고 설명하지 않는다.
- `MOCK MODE` 대화는 UI 흐름 검증이며 실제 Codex 또는 Ansys 응답으로
  설명하지 않는다. 모의 응답에서 생성·변경·해석이 완료됐다고 보고하지 않는다.
- 모델 생성·수정과 해석은 계속 Codex 자연어 흐름 및 기존 승인 경계를 따른다.

## 완료 보고

다음 항목을 짧게 보고한다.

- 실행한 자연어 목표와 대상 Workbench 시스템
- 생성·수정한 스크립트 및 결과 파일
- Ansys가 반환한 성공 또는 실패 상태
- 적용하지 않고 남겨둔 가정과 사용자가 확인할 공학적 항목
